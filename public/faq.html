QUESTIONS AND ANSWERS

Frequently asked questions

Honest answers about how AgentPay works and where it still falls short.

The basics
What is AgentPay in one sentence?
An autonomous payment system where a client agent and a worker agent transact USDC on Arc — the client escrows a fee, the worker classifies and completes the task, and payment settles or refunds the instant the result is verified.
Is this real money?
No — this runs on Arc Testnet with test USDC. The goal is proving the pattern works before any real deployment.
Why hold funds in escrow instead of paying directly?
So the client has a real window to review the work before funds settle permanently with the worker.
Is escrow handled by a smart contract?
Yes. AgentPayEscrow.sol is deployed on Arc Testnet, built on OpenZeppelin's audited primitives (ReentrancyGuard, Ownable, Pausable). Funds live in the contract itself, not in a server-controlled wallet.
What happens if the client disputes a result?
Within the 8-second window, the client can dispute and get an immediate refund — before the automatic release to the worker fires.
How payment actually moves
How are USDC transfers actually executed?
Escrow and settlement (createJob, release, dispute) call functions directly on the deployed smart contract via Circle's contract execution API. The USDC approval step also runs through Circle's wallet APIs, signed by the client's developer-controlled wallet.
Why Arc and USDC specifically?
USDC as native gas means the agents never need to hold a separate volatile asset just to pay network fees. Sub-second finality makes agent-to-agent payment practical at the speed agents actually operate.
Verification and quality
Who checks if the worker's answer is actually good?
A separate, independent model — not the one that produced the answer. It rejects vague non-answers and confidently-stated time-sensitive facts unless they carry an explicit outdated-information caveat.
Can the worker get paid for a bad answer?
The acceptance rules are type-specific: a summary must genuinely be shorter than the source, a sentiment analysis must return a valid classification with a reason, and a Q&A answer is rejected if the model admits it doesn't actually know.
Does the agent actually know about Arc and Circle, or just general knowledge?
Both the worker's answers and the independent verifier are given accurate, current background on Arc and Circle — sourced from official docs rather than generic training data, including specifics like Circle's June 2025 NYSE listing and Arc's planned summer 2026 mainnet launch. This closed a real bug: without this context, the verifier sometimes rejected correct historical facts as "possibly outdated" simply because it wasn't confident they were true.
Multi-worker and Nanopayments
How does the client pick which worker to use?
Two independent worker agents are available, each with its own wallet and wallet-linked reputation. Before creating a job, the client scores each worker on a combination of acceptance rate and price, then picks the winner — a real decision computed at runtime, not a fixed assignment.
What are Nanopayments, and why are they separate from the escrow flow?
Nanopayments (via Circle Gateway) handle sub-cent, gas-free payments for a single request — distinct from escrow, which is built for a complete task with verification and a dispute window. A dedicated wallet deposits USDC into Gateway, signs an EIP-3009 authorization, and pays a live protected endpoint. The full deposit-and-pay cycle runs server-side and can be triggered directly from the homepage.
Honest limitations
What's not finished yet?
Escrow is orchestrated by this server rather than an on-chain smart contract. There's only one worker agent today. Reputation is stored in a local file that can reset on redeploy.
If it's not production-ready, what's the point?
To demonstrate a working, tested proof of concept — real transactions on Arc Testnet, verified end-to-end. It shows the pattern works, not that it's finished.
